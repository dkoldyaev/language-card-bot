# Требования к тестированию (Test Requirements)

В данном документе описывается подход к написанию и организации тестов в проекте.

## 1. Стек тестирования
- **Test Runner:** [Vitest](https://vitest.dev/)
- **HTTP/API Тестирование:** [Supertest](https://github.com/ladjs/supertest)
- **База данных:** Prisma ORM
- **E2E Окружение:** Docker Compose (PostgreSQL, Redis, Mercure Hub, Mercure Monitor)

## 2. Архитектура и Структура Тестов
- **Расположение:** Интеграционные тесты пишутся по принципу Feature-Based архитектуры (рядом с кодом, `*.test.ts`), backend E2E — в `base/src/e2e/`, browser E2E — в `frontend/tests/`.
- **Scope (Область покрытия):** 
  - **Интеграционные тесты:** Проверяют работу модулей и бизнес-логики с использованием моков (БД, сторонних сервисов).
  - **End-to-End (E2E) тесты:** Проверяют работу всего пайплайна с использованием реальной БД (PostgreSQL), Redis и сервера Server-Sent Events (Mercure Hub).

## 3. Работа с Базой Данных

### В интеграционных тестах (`*.test.ts`)
- **Мокирование БД:** Тесты **не обращаются** к реальной базе данных. Вместо этого используется `vitest-mock-extended` для полного мокирования Prisma Client.
- **Изоляция:** Перед каждым тестом (`beforeEach`) необходимо сбрасывать состояние мока с помощью `mockReset(prismaMock)`.

### В E2E тестах (`*.e2e.test.ts`)
- **Реальная БД и инфраструктура:** Полный изолированный прогон запускается `npm run test:run-with-docker`: он поднимает отдельные PostgreSQL, Redis и Mercure в compose-проекте `language-cards-test`, затем вызывает `npm run test:e2e`.
- Используются настоящие тестовые PostgreSQL, Redis и Mercure; имена контейнеров не являются частью контракта тестов.
- **Изоляция:** Перед каждым тестом производится очистка тестовых данных (например, `prisma.user.deleteMany()`), чтобы гарантировать изоляцию стейта в реальной базе.

## 4. Изоляция и Мокирование (Mocking)
- **Внешние запросы в интеграционных тестах:** Все исходящие сетевые запросы (например, публикация событий в Mercure Hub через `fetch`) **должны быть замоканы**. Для этого используется `vi.fn()` или `vi.spyOn()`.
- **Глобальный Mock:** В таких тестах часто применяется глобальное мокирование `fetch` (например, `global.fetch = vi.fn().mockResolvedValue(...)`).
- **Внешние запросы в E2E тестах:** Запросы к Mercure не мокаются (события публикуются по-настоящему), однако запросы к сторонним AI/Translate API (вызовы микросервисов `translator` и `definer`) по-прежнему **мокаются**, чтобы избежать использования реальных ключей (Mistral, Gemini, Google Translate).
- **Проверка вызовов:** В тестах необходимо делать Assert на то, что замоканная функция была вызвана правильное количество раз и с корректными аргументами (URL, Headers, Body).
- **Prisma Client:** `PrismaClient` должен быть замокан с помощью `mockDeep<PrismaClient>()` из `vitest-mock-extended`, а его методы (`findUnique`, `create`, `update` и т.д.) переопределяются через `mockResolvedValue` прямо в теле теста (в секции Arrange).
- **Переменные окружения:** В хуке `beforeEach` тесты должны явно переопределять переменные окружения (`process.env`) на константные тестовые значения (например, `JWT_SECRET` и `MERCURE_URL`), чтобы поведение тестов не зависело от локального файла `.env`.

## 5. Структура Тестового Файла
Каждый тестовый файл должен иметь предсказуемую структуру:
1. **Импорты** (`vitest`, `supertest`, инстанс `app`, клиент `prisma` и т.д.).
2. **Блок `describe`** для группировки тестов одного эндпоинта или сервиса.
3. **Определение констант**, специфичных для данного набора тестов.
4. **Хук `beforeEach`**:
   - Переопределение `process.env`.
   - Настройка моков (`global.fetch` и т.д.).
   - Сброс состояния Prisma (`mockReset(prismaMock)`).
5. **Хук `afterEach`**:
   - Восстановление моков (`vi.restoreAllMocks()`).
6. **Блоки `it` (или `test`)** по паттерну *Arrange-Act-Assert*:
   - *Arrange*: Подготовка состояния (создание записей в БД через `prisma`, генерация тестовых JWT токенов).
   - *Act*: Выполнение HTTP-запроса через `request(app)`.
   - *Assert*: Проверка статус-кода ответа, структуры тела ответа (`res.body`), проверка изменений в базе данных и вызовов замоканных функций.

## 6. Лучшие практики (Best Practices)
- **Создание данных:** Для тестов, требующих наличия пользователя, мокайте ответы `prismaMock.user.findUnique.mockResolvedValue(...)` в секции Arrange.
- **Негативные сценарии:** Обязательно покрывайте тестами обработку ошибок (например, 401 Unauthorized при отсутствии токена, 400 Bad Request при неверной валидации).
- **Валидация Zod:** Так как Zod активно используется для парсинга ответов и запросов, интеграционные тесты выступают отличным способом проверить корректность описанных схем.

## 7. Тест как проверяемое требование

Каждый тест обязан доказывать наблюдаемое поведение, которое перестанет работать при регрессии. Перед добавлением теста надо письменно ответить на три вопроса: какое пользовательское или API-правило он защищает, каким действием правило запускается и какой внешний результат его подтверждает.

- Недостаточно просто отрендерить компонент, вызвать хук или проверить `expect(true).toBe(true)`. Такой тест не является проверкой.
- Нельзя оставлять ветку без assert: конструкция `if (элемент существует) { ... }` допустима только если обе ветки содержат разные обязательные проверки. Если элемент обязателен по сценарию, сначала использовать `expect(...).toBeVisible()`.
- Assert должен проверять результат, а не только вызов мока. Проверка аргументов мока полезна как дополнительная, но не заменяет проверку ответа, изменения состояния или видимого интерфейса.
- Тест не должен закреплять случайную деталь реализации: CSS-класс библиотеки, конкретный порядок случайной выборки, промежуточную структуру Zustand или текст мок-провайдера. Такие детали проверяются только если сами являются публичным контрактом.

## 8. Уровни тестов и границы моков

- **Unit:** чистая логика, преобразование данных и обработка входных вариантов. Внешние границы мокаются, но тест обязан проверить контракт вызова и результат обработки ответа.
- **Интеграционный API-тест:** маршрут, auth, Zod-валидация, права доступа и эффект в базе/очереди. Мок Prisma не отменяет негативные сценарии: отсутствие auth, чужой ресурс, неверный идентификатор и невалидное тело.
- **Инфраструктурный интеграционный тест:** реальная PostgreSQL, Redis и Mercure. Он проверяет доставку события с помощью ожидаемого события, а не фиксированной паузы.
- **Browser E2E:** пользователь делает действие через доступный интерфейс, затем тест наблюдает URL, доступное состояние и итог на экране. Не подменять этот путь чтением Zustand или `localStorage`, кроме отдельного теста именно на persistence.

E2E в этом проекте допускается запускать с mock-провайдерами словаря и перевода. В таком случае проверяется наш контракт с ними, а не качество внешнего AI. Реальные внешние API не должны быть скрытой зависимостью CI.

## 9. Маршрутизация и словари

Основной пользовательский тест перехода должен нажимать меню, селектор словаря или кнопку, а не подставлять адрес вручную. При этом у маршрута есть отдельный контракт, который обязательно проверяется компактным тестом:

- действие пользователя строит канонический URL с locale и id словаря/пресета;
- обновление страницы на полученном URL показывает тот же ресурс;
- невалидный или устаревший URL не открывает другой словарь и не запускает создание словаря;
- защищённый маршрут проверяется прямым открытием адреса как проверка boundary, а не как замена пользовательской навигации.

Создание словаря остаётся действием модального окна. Тесты не должны превращать `/dictionary/new` в пользовательский сценарий.

## 10. Асинхронность, SSE и надёжность

- Не использовать `sleep`, `setTimeout(500)` и повторные reload как способ дождаться события. Хелпер должен ожидать конкретное сообщение, состояние очереди или доступный элемент с ограниченным таймаутом и диагностикой.
- Для Mercure нужны две независимые проверки: backend публикует событие в правильный topic, а браузер с тем же topic применяет каждое поддерживаемое событие к UI. Общий env в двух сторонах не доказывает их совместимость.
- Длинный E2E-сценарий должен быть разбит, если в нём больше одного бизнес-правила. Один сбой должен указывать на конкретную возможность, а не маскировать все последующие.
- Каждый тест создаёт собственные данные, не зависит от порядка и не опирается на предзагруженные пресеты. Общая очистка охватывает БД, Redis, очереди и browser storage, которые влияют на сценарий.

## 11. Селекторы и наблюдаемые результаты

- Приоритет селекторов: роль и доступное имя, затем стабильный `data-testid`, затем локальный текст. Нельзя строить ключевую проверку на `.Mui*`, DOM-иерархии или `nth()` без собственного test id.
- Для динамического списка тест должен искать элемент внутри конкретной карточки/строки, а не первый совпавший элемент на странице.
- Проверки локального состояния допустимы только для отдельного контракта offline/persistence. Пользовательский E2E подтверждает тот же эффект после reload либо через видимый интерфейс.

## 12. Обязательный минимум для нового поведения

При изменении функции добавляется тест на успешный сценарий и на наиболее опасный отказ. Для новых прав доступа обязательны guest, unauthenticated и чужой ресурс, когда это применимо. Для нового SSE-сообщения обязательны: публикация, разбор браузером и видимое изменение интерфейса. Для нового URL обязательны: переход через UI и reload/copy-link контракт.
