# Технические требования и архитектура

## 1. Стек технологий
- **Язык**: TypeScript.
- **Платформа**: Node.js (версия 22+, `tsx` для dev-режима, `tsc` для продакшена).
- **Веб-фреймворк**: Express.js.
- **База данных**: PostgreSQL, Redis (для очередей и кэширования).
- **ORM**: Prisma ORM (используется для миграций и типизированного взаимодействия с БД).
- **Валидация и Типизация**: Используется **Zod** для runtime-валидации данных (Request / Response / Mercure Events) и автоматического вывода TypeScript-типов.
- **Тестирование**: Vitest + Supertest (см. подробнее в [test-requirements.md](./test-requirements.md)).
- **Сторонние API**: Google Translate API, Mistral API, Gemini API (используются для перевода и получения определений).

## 2. Структура и Инфраструктура (Микросервисы)
- Проект построен на микросервисной архитектуре. Все сервисы запускаются через Docker Compose:
  - `base` — основное Express API. В нем реализована бизнес-логика (Feature-Based структура в `base/src/features`), работа с БД и авторизация.
  - `mercure` — шина событий (Mercure Hub) для Server-Sent Events (SSE).
  - `translator` — микросервис для перевода слов с использованием Google Translate API.
  - `definer` — микросервис для получения определений слов с использованием AI (Mistral, Gemini).
  - `mercure_monitor` — вспомогательный сервис для мониторинга событий Mercure, используемый при отладке и тестировании.
- **Контейнеризация**: Каждый сервис имеет собственный `Dockerfile` (multi-stage на базе `node:22-alpine` для Node.js приложений).
- **Работа с БД**: Для хранения данных используется PostgreSQL, а для очередей задач (BullMQ) — Redis.

## 3. API и Авторизация
- **Rest API**: Основной способ взаимодействия с сервисом. 
- **Версионирование**: Все эндпоинты маршрутизируются с указанием версии (напр., `/api/v1/`).
- **Авторизация**: Реализована при помощи JWT (JSON Web Tokens). Токен передается в заголовке `Authorization: Bearer <token>`.
- **Клиенты**: В текущей архитектуре сервис работает исключительно как API. Интеграция с Telegram-ботами или клиентскими приложениями происходит на их стороне.

## 4. Real-time уведомления (Mercure)
- **Шина сообщений**: Используется Mercure Hub для отправки Server-Sent Events (SSE).
- **Отправка данных**: Бэкенд делает POST-запросы к Mercure API для публикации событий. В полезной нагрузке сообщений всегда передается поле `version` (например, `version: 'v1'`).
- **Изоляция (Приватные обновления)**: Данные пользователей изолируются через персональные топики вида `http://localhost/v1/users/{username}/*`. 
- **Безопасность клиента**: Для прослушивания топика клиент должен получить с бэкенда специальный Mercure JWT-токен, в котором поле `mercure.subscribe` ограничивает доступ только личным топиком пользователя.

## 5. Асинхронные задачи
- Сервис поддерживает асинхронное выполнение фоновых задач. В частности, получение переводов и определений при добавлении новых слов происходит в фоне, чтобы не блокировать ответ API.
- Реализована полноценная очередь задач с использованием **BullMQ** и **Redis** (настроены очереди и воркеры в соответствующих фичах, например `add_word.queue.ts`).

## 6. Управление переменными окружения (Environment Variables)
- **Глобальный конфигурационный файл**: В корне проекта находится единый агрегированный файл `.env` (и шаблон `.env.example`), содержащий переменные для всех микросервисов. Для избежания конфликтов имена переменных дополняются префиксом сервиса (например, `BASE_DATABASE_URL`, `FRONTEND_VITE_API_BASE_URL`).
- **Локальные конфигурации микросервисов**: В директории каждого микросервиса (например, `base/`, `frontend/`) содержится только один рабочий файл `.env` (и его шаблон `.env.example` с комментариями), предназначенный исключительно для локального запуска (без использования Docker). Использование дополнительных файлов, таких как `.env.test`, на уровне микросервисов не допускается.
- **Docker Compose (production/dev)**: В файле `docker-compose.yml` запрещено жесткое кодирование (хардкод) значений конфигурации. Все переменные контейнеров должны динамически транслироваться из глобального `.env` (например, `DATABASE_URL=${BASE_DATABASE_URL}`).
- **Docker Compose (test)**: В файле `docker-compose.test.yml` тестовые переменные окружения определяются непосредственно внутри самого yaml-файла (например, явное задание `POSTGRES_USER` и конструирование `DATABASE_URL`). Это позволяет запускать тестовое окружение изолированно без необходимости создания отдельного корневого файла `.env.test`.
